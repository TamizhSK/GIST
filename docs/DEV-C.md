## What this log is

A `yeet run` of a workflow whose `manual_checkout` job installs git, clones a
repository by hand, and verifies it. The clone failed:

```
remote: Invalid username or token. Password authentication is not supported for Git operations.
fatal: Authentication failed for 'https://github.com/Tamizhazhagan-SK/ghactions.git/'
```

## What was done about it

| # | Report | Fix |
|---|---|---|
| 1 | A hand-written `git clone` fails inside the container while working on the host | A container is a fresh machine: no SSH agent, no `~/.gitconfig`, no credential helper, no keychain. `core/gitcreds.py` finds a token you already have (`.yeet/.secrets`/`.env` → `$GITHUB_TOKEN`/`$GH_TOKEN` → `gh auth token` → your own git credential helper) and serves it to every container through a git credential helper that reads it from the environment at step time. The token is therefore never a config *value* — it stays out of `git config --list`, git's error text and any `set -x` — and it is added to the `Masker`. `actions/checkout` was never the whole story; this covers `clone`, `fetch`, `ls-remote` and `pip install git+https://…` alike. |
| 2 | A private repo hangs instead of failing | `GIT_TERMINAL_PROMPT=0`. git was blocking on `Username for 'https://github.com':` against a terminal the container does not have, so the step sat until its timeout with nothing in the log. It now fails in under a second, and a recognised auth failure prints a hint that differs depending on whether a token was passed. |
| 3 | `git` in the bind-mounted workspace fails on "dubious ownership" | `safe.directory=*`, delivered through `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` so nothing is written into the user's working tree. The mount is owned by a uid that does not exist inside the image; the message is about our mount, not their repository. |
| 4 | `git@github.com:` can never work in a container | Rewritten to HTTPS via `insteadOf`. There is no SSH key and no agent in there. The rewrite carries no credentials, so a public repo clones with or without a token. |
| 5 | "no Docker daemon is listening" while `docker ps` works | `docker.from_env()` reads `$DOCKER_HOST` and nothing else; the CLI reads `docker context`. Colima, Rancher Desktop, Podman, Lima and rootless dockerd all create a context and never export the variable. yeet now reads the same context file, then falls through every well-known socket on macOS/Linux/WSL and both Windows named pipes, and exports whichever answers so the `docker` binary agrees. |
| 6 | The Windows daemon error printed raw | `open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified` had no translation — the most common Docker failure on the most common desktop OS was the one case falling through to the catch-all. Translated, along with "Access is denied" and a pipe that dies mid-run. |
| 7 | The daemon error appeared once per job, mid-render | A preflight connects once before the run starts, so a five-job workflow prints one error, before the live tree takes the terminal. Exit 3, unchanged. |
| 8 | Where do secrets go, given GitHub's are write-only? | They cannot be fetched — `GET /actions/secrets` has no `value` field, so no local runner can sync them. E307 now names both local paths (`.yeet/.secrets`, `.env`) and says why; `yeet secrets import` marks names that are `set on GitHub (value not readable)`; [`docs/secrets.md`](docs/secrets.md) is the full answer. |
| 9 | `yeet init` did not actually ignore the secret store | `GITIGNORE_BLOCK` had `.yeet/.secrets/` — a trailing slash matches directories only, and that is a file. Every project initialised by yeet was one `git add -A` from committing its own encrypted store, silently. |

**Proved on this machine:** the workflow above, re-run against a public repo,
now passes all three steps; the token is masked (`***`) and absent from
`.yeet/runs/`; a bogus `$DOCKER_HOST` still finds the daemon; and with no daemon
at all the run exits 3 with two readable lines.
